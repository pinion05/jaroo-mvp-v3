# OCR 손익 부호 및 평단 계산 개선 설계

## 배경

일부 국내 증권사 보유종목 화면은 손실 행을 `-13,263 (6.8%)`처럼 표시한다. 손실 부호는 평가손익 금액에만 있고 괄호 안 수익률에는 없다. 현재 OCR 계약은 `profitRate`만 구조화하고 평가손익 금액을 버리므로, 모델이 `6.8%`만 반환하면 양수로 해석되어 잘못된 평단과 손익이 저장된다.

## 목표

- 평가손익 금액의 부호를 손익 방향의 우선 근거로 사용한다.
- 평가손익 금액이 있으면 반올림 수익률이 아니라 정확한 금액으로 원가와 평단을 계산한다.
- 기존 OCR 응답과 저장 데이터는 계속 처리한다.
- 실제 제보 JPEG로 OCR, 종목 식별, 현재 시세, 최종 손익까지 검증한다.

## 비목표

- 이번 변경에서 DB 스키마에 OCR 원본이나 촬영시각을 영구 저장하지 않는다.
- 홈 화면 레이아웃이나 종목 식별 알고리즘을 변경하지 않는다.
- 기존 저장 포트폴리오의 잘못된 평단을 원본 없이 자동 복구하지 않는다.

## 데이터 계약

OCR 행에 선택적 문자열 필드 `profitAmount`를 추가한다.

- `profitAmount`: 행에 보이는 평가손익 금액. 예: `+262,740원`, `-13,263원`.
- `profitRate`: 항상 방향을 포함한 수익률. 예: `+12.7%`, `-6.8%`.
- strict JSON schema에서는 모델이 일관된 형태를 반환하도록 `profitAmount`를 필수 문자열로 요구하되, 읽을 수 없거나 없는 화면은 빈 문자열을 반환한다.
- 클라이언트 타입과 sanitizer에서는 구형 응답 호환을 위해 선택적으로 취급한다.

## 정규화 규칙

1. `profitAmount`가 직접 제공되면 부호를 포함한 단일 금액으로 정규화한다.
2. 구형 모델이 `profitRate`에 `-13,263 (6.8%)` 전체를 넣으면 앞부분에서 `profitAmount`를 복원한다.
3. 수익률 자체에 부호가 없으면 정규화된 `profitAmount`의 부호를 상속한다.
4. 수익률에 명시적 부호가 있어도 `profitAmount`와 충돌하면 같은 행의 손익금 부호를 우선한다. 평가손익 금액이 실제 손익 방향과 정확한 원가를 동시에 제공하기 때문이다.
5. 손익금과 수익률을 모두 해석할 수 없으면 기존처럼 빈 값 또는 수익률 기반 fallback을 사용한다.

## 평단 및 손익 계산

평가손익 금액이 유효할 때:

```text
원금 = 평가금액 - 평가손익금
평단 = 원금 / 수량
```

조건:

- 수량은 0이 아니어야 한다.
- 평가금액, 평가손익금, 계산된 원금은 유한한 숫자여야 한다.
- 원금은 0보다 커야 한다.

조건을 만족하지 않거나 평가손익 금액이 없으면 기존식을 사용한다.

```text
원금 = 평가금액 / (1 + 수익률 / 100)
평단 = 원금 / 수량
```

이후 live quote 계산은 기존대로 `현재 평가액 - 저장 원가`를 사용한다. 이번 변경은 live quote 로직을 바꾸지 않고 그 입력인 원가를 정확하게 만든다.

## 적용 범위

- `src/app/api/ocr/route.ts`
  - OCR JSON schema에 `profitAmount` 추가
  - 국내 증권사 결합 표기와 부호 상속 규칙을 프롬프트에 명시
- `src/lib/screenshot-ocr.ts`
  - 손익금 및 수익률 정규화
  - 손익금 우선 평단 계산
  - sanitizer에서 구형/신형 응답 모두 처리
- OCR workflow 타입 및 handoff
  - `profitAmount`를 검수·적용 단계까지 전달
  - 다계좌 동일 종목 병합 시 손익금을 합산하고 합산 원가 기준 수익률을 계산
  - 적용된 평단은 기존 portfolio item/DB 필드에 저장
- OCR 검수 UI
  - 기존 직접 수정 패널에 선택 입력인 `평가손익`을 추가
  - 수익률·평가금액·평가손익 중 하나를 수정하면 같은 금액 우선 규칙으로 평단을 즉시 재계산

## 오류 처리 및 호환성

- `profitAmount`가 빈 문자열이면 기존 동작을 유지한다.
- 결합 문자열에서 손익금을 추출하지 못해도 수익률 파싱은 계속 시도한다.
- 잘못된 손익금 때문에 원금이 0 이하가 되면 금액 기반 계산을 버리고 수익률 fallback을 사용한다.
- 기존 DB에는 평단과 평가금액이 있으므로 migration 없이 계속 로드할 수 있다.
- API fallback 모델이 schema-free JSON을 반환해도 sanitizer가 누락 필드를 허용한다.

## 테스트 전략

### 단위 회귀 테스트

실제 제보 행을 기반으로 다음을 먼저 실패하도록 추가한다.

- `profitAmount: -13,263원`, `profitRate: 6.8%`가 `-6.8%`로 정규화된다.
- 구형 결합 값 `-13,263 (6.8%)`에서 손익금과 음수 수익률이 복원된다.
- SOOP 평단이 `64,800원`으로 계산된다. 이는 `(181,137 - (-13,263)) / 3`이다.
- 수익 행은 `(2,320,500 - 262,740) / 35 = 58,793.1429원`으로 계산된다.
- 손익금이 없으면 기존 수익률 역산 결과를 유지한다.
- 비정상 손익금으로 원금이 0 이하이면 fallback한다.

### API 계약 테스트

- OCR prompt에 결합 표기와 부호 상속 예시가 포함된다.
- JSON schema가 `profitAmount`를 허용하고 필수 문자열로 요구한다.

### 기존 회귀 테스트

- OCR, review aggregation, portfolio apply/sync, home quote 테스트를 실행한다.
- TypeScript, ESLint, Next build를 검증한다.

3. 계산된 평단이 원본 평가금액과 손익금을 정확히 재구성한다.

## 성공 기준

- 제보 이미지의 손실 3개 종목이 OCR 모델의 unsigned 괄호 수익률에도 음수로 처리된다.
- 원본 손익금으로 계산한 평단과 초기 손익이 반올림 수익률 역산보다 정확하다.
- 구형 OCR 응답 및 기존 포트폴리오 저장 데이터가 깨지지 않는다.
- 자동 테스트, 타입 검사, lint, build, 실제 이미지 라이브 검증을 모두 통과한다.
